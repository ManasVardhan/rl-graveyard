# RL Graveyard v1 — Design Spec

**Date:** 2026-06-05
**Audience:** Portfolio / OSS showcase
**Status:** Pending review

## 1. Vision

A public, interactive catalog of RL failure modes. Most RL writing celebrates success curves; this project documents the much larger graveyard of runs that crash, plateau, or hack their reward. The artifact is a website ("the graveyard") backed by real training data, where each dead agent gets a tombstone, a death certificate, and a post-mortem.

The thesis the showcase has to support: **which algorithms fail on which environments, and why.**

## 2. v1 Scope

### In

- **6 algorithms** (all discrete-action):
  - **PPO** — clipped surrogate + GAE + minibatch updates
  - **A2C** — synchronous, n-step returns
  - **REINFORCE** — classical Monte-Carlo policy gradient (no baseline first, optional baseline variant)
  - **DQN** — replay buffer, target network, ε-greedy
  - **Double DQN** — DQN with decoupled action selection/evaluation in the TD target
  - **Dueling DQN** — DQN with separate value and advantage streams
- **5 environments**: `CartPole-v1`, `Acrobot-v1`, `MountainCar-v0`, `LunarLander-v2`, and a custom `RewardTrap-v0` gridworld designed to be exploitable
- **5 seeds × 200K steps** per (algo, env) cell → 150 training runs total
- **6 failure modes**: Reward Hacking, Exploration Collapse, Death Spiral, NaN Explosion, Stalling, Overshooting
- **SQLite** as the run store (committed to repo so the frontend can read it without infrastructure)
- **Next.js + Tailwind frontend**, statically exported, deployed to Vercel
- **Per-mode failure classifier** with unit tests against synthetic trajectories
- **Hashnode writeup** at launch

### Out (v2+)

- SAC, TD3 (continuous-action only — would force adding continuous envs and roughly double the matrix)
- Catastrophic Forgetting (requires multi-task curricula like Meta-World/Procgen)
- Simulation Overfitting (requires train/test perturbation harness)
- 1M-step runs (200K is sufficient to surface failure modes; 1M is paper-grade)
- Atari, MuJoCo (compute-heavy, off-message for a showcase)
- Live training viewer (post-hoc autopsy is the v1 story)

## 4. Component design

### 4.1 Agent interface

```python
class Agent(ABC):
    def act(self, obs: np.ndarray) -> tuple[int, dict]:
        """Return (action, info dict with log_prob, value, entropy)."""

    def update(self, batch: Trajectory) -> dict:
        """Train on a trajectory; return metrics (loss, grad_norm, entropy)."""

    def state_dict(self) -> dict: ...
```

Each algorithm gets its own file. No shared "trainer" base class — each algorithm has its own training loop because their data collection patterns differ (PPO/A2C on-policy vs DQN off-policy with replay). Shared concerns (logging, checkpointing) live in `experiments/runner.py`.

### 4.2 Environment registry

```python
@dataclass(frozen=True)
class EnvMeta:
    name: str
    factory: Callable[[int], gym.Env]  # seed → env
    max_steps: int
    success_threshold: float
    act_type: Literal["discrete", "continuous"]

REGISTRY: dict[str, EnvMeta] = {...}
```

`LoggingWrapper` records per-step `entropy`, `grad_norm`, `value_estimate`, `reward` and per-episode `return`, `length`, `success`. These are appended to in-memory buffers and bulk-written to SQLite when an episode ends or every N steps.

### 4.3 RewardTrap env

A 10×10 gridworld. Agent starts top-left, designated goal is bottom-right (+10 reward, terminates). A trap square gives +0.1 reward every step the agent stays on it, never terminates. PPO under default hyperparams will discover the trap, never reach the goal, and the classifier should flag this as Reward Hacking.

### 4.4 Failure classifier

Each mode gets its own detector function with documented thresholds. `diagnose()` runs them in priority order (NaN first because it short-circuits everything else) and returns the first match.

```python
def detect_nan_explosion(traj: Trajectory) -> Optional[Verdict]: ...
def detect_exploration_collapse(traj: Trajectory) -> Optional[Verdict]: ...
def detect_death_spiral(traj: Trajectory) -> Optional[Verdict]: ...
def detect_stalling(traj: Trajectory) -> Optional[Verdict]: ...
def detect_overshooting(traj: Trajectory) -> Optional[Verdict]: ...
def detect_reward_hacking(traj: Trajectory) -> Optional[Verdict]: ...

DETECTORS = [detect_nan_explosion, detect_exploration_collapse, ...]

def diagnose(traj: Trajectory) -> Verdict:
    for d in DETECTORS:
        if (v := d(traj)) is not None:
            return v
    return Verdict("alive", "Agent reached training budget")
```

Each detector is unit-tested with hand-crafted synthetic trajectories. Thresholds are documented in code with a `# Why this threshold:` comment per detector — these are the methodology decisions reviewers will ask about.

The current `graveyard.py:diagnose_death` is too brittle to keep (the reward-hacking detector triggers on any spike). Replaced wholesale.

### 4.5 SQLite schema

```sql
CREATE TABLE runs (
    id INTEGER PRIMARY KEY,
    algo TEXT NOT NULL,
    env TEXT NOT NULL,
    seed INTEGER NOT NULL,
    total_steps INTEGER NOT NULL,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    hparams_json TEXT NOT NULL,
    UNIQUE(algo, env, seed)
);

CREATE TABLE episodes (
    run_id INTEGER REFERENCES runs(id),
    episode_idx INTEGER,
    return_ REAL,
    length INTEGER,
    success INTEGER,
    PRIMARY KEY(run_id, episode_idx)
);

CREATE TABLE step_metrics (
    run_id INTEGER REFERENCES runs(id),
    step INTEGER,
    entropy REAL,
    grad_norm REAL,
    value_estimate REAL,
    PRIMARY KEY(run_id, step)
);

CREATE TABLE autopsies (
    run_id INTEGER PRIMARY KEY REFERENCES runs(id),
    failure_mode TEXT NOT NULL,
    cause TEXT NOT NULL,
    classified_at TEXT NOT NULL
);
```

`step_metrics` is downsampled (one row per 100 environment steps) to keep the committed DB under ~50MB.

### 4.6 Experiment runner

```python
@dataclass
class ExperimentConfig:
    algo: str
    env: str
    seed: int
    total_steps: int = 200_000
    hparams: dict = field(default_factory=dict)
```

`runner.train_and_record(config)`:
1. Construct agent + wrapped env from registry
2. Run training loop, streaming metrics to in-memory buffers
3. Flush buffers to SQLite at episode end
4. After training, run `diagnose()` and insert autopsy row
5. Return run_id

Crash recovery: each run is independent; if Modal kills a container mid-run, the row exists with `finished_at IS NULL` and is re-run on the next sweep.

### 4.7 Modal integration

```python
@app.function(image=image, gpu="T4", timeout=3600)
def run_one(config: ExperimentConfig) -> int: ...

@app.local_entrypoint()
def sweep():
    configs = load_grid("experiments/grid.yaml")
    results = list(run_one.map(configs))
```

DQN benefits from GPU (replay buffer + gradient steps); PPO/A2C on classic control are CPU-fine. The Modal config gates GPU on algorithm: T4 for DQN runs, CPU containers for PPO/A2C runs.

### 4.8 Frontend

**Build-time data flow**: `scripts/export_json.py` reads `data/graveyard.sqlite` and writes static JSON files (`graveyard/public/data/runs.json`, `compare.json`, `stats.json`). The Next.js app reads these at build time — no runtime DB connection, no API routes needed. Pure static export to Vercel.

**Pages**:
- **Landing** (`/`): hero banner, then a grid of tombstones — one per (algo, env, seed) run. Tombstones color-coded by failure mode. Click → detail page.
- **Detail** (`/run/[id]`): the death certificate as a centered card (already templated in `graveyard.py:print_death_certificate`; port to JSX). Below: three time-series charts (return, entropy, grad norm) annotated with the moment of classification. Plain-language autopsy paragraph.
- **Compare** (`/compare`): heatmap, rows = algos, cols = envs, each cell shows the dominant failure mode across 5 seeds.
- **Stats** (`/stats`): donut chart of failure-mode distribution overall; stacked bar of failure modes per environment.

**Components**:
- `Tombstone` — SVG headstone shape, algo name engraved, dates (run start → death), CSS hover lift
- `DeathCertificate` — typographic, mimics the ASCII version in the current `graveyard.py`
- `TrajectoryChart` — Recharts LineChart with classification-point annotation

**Aesthetic**: lean into the metaphor without going kitsch. Muted color palette (slate, bone, blood-red for failed, faded green for survived). Serif headings for the certificates (gravitas), monospace for the data.

## 5. Build phases

### Phase 1 — Backend skeleton (3-4 focused days, no GPU)
1. Package layout; deprecate `graveyard.py` as entrypoint (keep file for one commit's continuity, then delete)
2. `agents/base.py` + `agents/ppo.py` + `agents/a2c.py` + `agents/reinforce.py`
3. `agents/replay.py` + `agents/dqn.py` (DQN, then Double DQN as subclass, then Dueling DQN as subclass)
4. `envs/registry.py` + `envs/wrappers.py`
5. `envs/reward_trap.py` (and verify PPO under default hparams falls into the trap on at least 3/5 seeds)
6. `data/schema.sql` + `data/db.py`
7. `experiments/config.py` + `experiments/runner.py`
8. `analysis/diagnose.py` with all 6 detectors + tests
9. Smoke test: each of the 6 algos on CartPole writes to SQLite, diagnose runs cleanly

### Phase 2 — Run the grid (1 day setup + compute time)
1. Author `experiments/grid.yaml` (150 configs)
2. `experiments/modal_app.py` with per-algo image/GPU specialization
3. Execute sweep, monitor for stuck containers
4. Verify failure-mode coverage. If everything just "survives": tune hparams downward (smaller nets, higher LR, lower entropy bonus) to provoke failure — this is part of the methodology, not a regression
5. Spot-check 5 random runs manually to verify classifier correctness

### Phase 3 — Frontend (3-4 days)
1. `graveyard/` Next.js + Tailwind scaffold
2. `scripts/export_json.py` and wire into build
3. `Tombstone`, `DeathCertificate`, `TrajectoryChart` components
4. Four pages
5. Deploy to Vercel (custom domain optional)

### Phase 4 — Polish & launch (1 day)
1. Rewrite `README.md` with screenshots, real numbers, link to live site
2. Hashnode post
3. Optionally: social cards for sharing

## 6. Non-negotiable methodology guardrails

These are the things that, if cut, would make the artifact intellectually embarrassing:

- **Real PPO**, not the current 1-step A2C labeled as PPO. The README cites the algorithm by name; the code must deliver.
- **5 seeds minimum** per cell. Single-seed results are noise.
- **Classifier unit tests** with synthetic trajectories. Without these, the classifier's verdicts are vibes.
- **Documented thresholds**. Every magic number in `diagnose.py` needs a one-line `# Why:` comment.
- **Hyperparameters logged** to `runs.hparams_json`. Reproducibility floor.
